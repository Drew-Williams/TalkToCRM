name: CRM OAuth v1
description: Why HubSpot/Pipedrive OAuth in a Chrome extension uses chrome.identity + a POST exchange endpoint instead of the GET redirect-callback pattern from salesplaybookbuilder-ai, plus the crm_connections/crm_writes schema and the normalized DealSnapshot contract
type: design
---

**Why this deviates from the main repo's OAuth callback pattern.** `salesplaybookbuilder-ai`'s `hubspot-oauth-callback`/`pipedrive-oauth-callback` are GET endpoints: the browser navigates there directly (HubSpot/Pipedrive redirect it after consent), the function exchanges the code for tokens, then 302-redirects the browser back into the web app. That only works because there's a real web app with an origin to redirect back to.

A Chrome extension has no such origin to redirect to, and MV3 extension pages can't be the target of an arbitrary HTTPS redirect anyway. The standard pattern is `chrome.identity.launchWebAuthFlow`: the extension opens the CRM's consent screen with `redirect_uri` set to `chrome.identity.getRedirectURL()` (a stable `https://<extension-id>.chromiumapp.org/` URL). Chrome intercepts navigation to that URL internally — it's never actually requested over the network — and resolves the `launchWebAuthFlow` promise with the final URL (containing `code`/`state`) directly in the extension's JS. That means the token exchange has to be a **POST the extension itself calls** with the code it already has, not a GET the CRM's redirect lands on. Hence `hubspot-oauth-exchange`/`pipedrive-oauth-exchange` (`supabase/functions/`) instead of `*-oauth-callback`.

**Client ID vs secret.** OAuth client IDs (`VITE_HUBSPOT_CLIENT_ID`, `VITE_PIPEDRIVE_CLIENT_ID`) are public and safe to bundle into the extension — the authorize URL is built client-side. Client secrets never leave the edge functions (`HUBSPOT_CLIENT_SECRET`, `PIPEDRIVE_CLIENT_SECRET` as Supabase secrets), consistent with the same client/server secret split as the Supabase keys.

**Linking an email is OTP, not a magic link** (superseded: this used to describe the *first* sign-in step too, before the reverse-trial pivot — see `mem/design/reverse-trial-v1.md`). A magic link opens in a new browser tab; there's no reliable way to get that tab's resulting session back into the side panel's own document. A typed 6-digit code needs no redirect at all — used both for the original `signInWithOtp`/`verifyOtp(type: "email")` sign-in pair, and now for `LinkAccountBanner.tsx`'s `updateUser`/`verifyOtp(type: "email_change")` pair that upgrades an anonymous session to a permanent one.

**crm_connections is per (user_id, provider), tokens never reach the client.** Edge functions read/write the base table with the service role key. The extension only ever reads `crm_connections_status`, a `security_invoker` view exposing `provider`/`account_ref`/`scopes`/`created_at` — no `access_token`/`refresh_token` columns — so there's no path for a raw CRM token to end up in the extension bundle's memory or dev tools.

**DealSnapshot is the only shape client tools ever see.** `supabase/functions/_shared/deal-snapshot.ts` defines the normalized shape both adapters (`crm-hubspot.ts`, `crm-pipedrive.ts`) return from `getDeal()`. `crm-proxy` is the single edge function that picks the adapter, refreshes the token if it's within 5 minutes of expiry, and returns this shape — HubSpot's and Pipedrive's very different raw API responses never leak past the adapter layer. This is what "ElevenLabs client tools never see provider-specific shapes" (project brief) means in code.

**crm_writes exists before anything writes to it.** The table (and its RLS: select-only for `authenticated`, all writes via service role) is created in step 2 alongside `crm_connections` even though nothing inserts into it until `push_to_crm` lands, so the schema — including the 24h `reversible_until` window and the verbatim `readback_text`/`confirmation_text` audit fields for the two-step write contract — is stable before that code exists.
