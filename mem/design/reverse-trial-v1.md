---
name: Reverse trial v1
description: Why Corner has no landing-page sign-up at all — install-first via an anonymous Supabase user, trial tracked from account creation, email captured mid-trial, payment collected only at day 7 — and how that changed auth, the subscriptions schema, and the Stripe functions from the original (landing-page checkout, email/card upfront) design
type: design
---

**The funnel, and why it changed.** The original design (see git history on this file's introduction) put Stripe Checkout — email, then a card, then a 7-day Stripe-side trial — on the marketing site, *before* installing anything. The marketing site (built in Lovable) proposed inverting this: "Add Corner to Chrome" with no form at all, a free trial that starts the moment the extension is opened, email captured only once the rep has had a session or two (to "save" their trial), and a card only requested at the hard paywall on day 7. This is a "reverse trial" / product-led-growth pattern — remove every point of friction between "saw the landing page" and "experienced the product," and monetize only after value is delivered. Adopted because it's a materially better conversion funnel, at the cost of a real rearchitecture: the extension can no longer assume a rep has signed in (or even exists as an account) before using it.

**The trial starts at `auth.users` insert, not at some "start trial" call.** `useSupabaseSession.ts` calls `supabase.auth.signInAnonymously()` the instant there's no existing session — invisibly, no UI, before the rep does anything. A Postgres trigger, `handle_new_user_trial` (`supabase/migrations/20260727190000_reverse_trial.sql`), fires on every `auth.users` insert — anonymous or a normal email sign-up — and creates a `subscriptions` row with `status = 'trialing'`, `trial_end = now() + 7 days`. There is deliberately no separate "start trial" endpoint: every account, however it comes to exist, gets the same 7 days, and this can't be skipped or forgotten by application code.

**Anonymous users are real Supabase users, not a local-only concept.** `supabase.auth.signInAnonymously()` creates an actual `auth.users` row with `is_anonymous: true` on its JWT — RLS-visible, `crm_connections`-capable, everything a permanent user can do, except it has no recovery path at all: sign out, clear browser data, or reinstall, and it's gone forever with no email to get it back. This is why `App.tsx` hides the "Sign out" button entirely until `!session.user.is_anonymous` — for an anonymous session, "sign out" is equivalent to "delete everything," with no warning a rep would expect from that label.

**Linking an email upgrades the same account; it doesn't create a new one.** `LinkAccountBanner.tsx` (the "day 5 of 7" soft nudge — see `useSubscription.ts`'s `shouldNudge`, gated on `is_anonymous && trialing && trial_end` within `NUDGE_WINDOW_DAYS`) uses Supabase's anonymous-identity-linking flow: `updateUser({ email })` followed by `verifyOtp({ email, token, type: "email_change" })`. This requires two project-level Auth settings enabled beyond anonymous sign-ins themselves — `external_anonymous_users_enabled` and `security_manual_linking_enabled` — and, like the original sign-in flow, needed its own email template fix: `mailer_templates_email_change_content` only rendered `{{ .ConfirmationURL }}` out of the box, no visible code, same defect already hit and fixed on `mailer_templates_magic_link_content`/`mailer_templates_confirmation_content` for the original sign-in flow.

**The day-7 paywall lives in the extension, not the marketing site.** There is no landing-page Stripe Checkout anymore. `stripe-create-checkout-session` now requires a caller JWT (`getCallerUser`, same as every other function except the webhook) instead of accepting an arbitrary email from an unauthenticated request, specifically so it can pass the caller's *existing* Supabase user id through to Stripe as `client_reference_id`. This matters because a rep can validly reach the paywall still fully anonymous (skipped the day-5 nudge) — Stripe still collects an email as a normal part of taking payment, but `client_reference_id` is what lets `stripe-webhook`'s `checkout.session.completed` handler attach that payment to the account the rep was already using all week, backfilling the email Stripe collected onto it, rather than creating a second, disconnected account. The original email-based find-or-create in that handler is now only a fallback for a checkout session created some other way (e.g. manually in the Stripe Dashboard) with no `client_reference_id` set. No `trial_period_days` on the Stripe subscription either — the free trial already happened before checkout; the paid subscription Stripe creates starts `active` immediately, not another Stripe-side `trialing`.

**Checkout can't happen inside the side panel.** Stripe's hosted Checkout page refuses to be iframed (standard payment-processor security posture), so `PaywallView.tsx` opens it via `chrome.tabs.create` in a real tab, and polls `subscription_status` every 5 seconds while that's open to notice the webhook-driven update — no `postMessage`/`externally_connectable` handshake needed for this particular handoff, since the *extension* both starts the checkout and is the thing that needs to notice it finished, unlike the (still undecided/deferred) "skip re-entering your email after Chrome Web Store install" handoff described in `docs/lovable-integration.md`, which is a different problem — connecting a stateless first launch back to something that happened on the marketing site.

**What the marketing site owns now: nothing but a link.** No email capture, no Stripe integration, no `/welcome?session_id=...` query-string handling — just an "Add Corner to Chrome" button pointing at the Chrome Web Store listing (`chromeStoreUrl` on their side, a placeholder until Corner is actually published) and a lightweight post-install `/welcome` page the extension can link to after first launch. Everything else — trial tracking, email capture, payment — lives entirely in this repo.
